§1 — Executive Summary
Section 01

Executive Summary

NYX is a terminal-native, distributed messaging and developer communication platform designed for engineers, security researchers, infrastructure operators, and technical communities. Named after Nyx — the Greek personification of night — the system embodies darkness, silence, mystery, and the unknown as design philosophy, not fantasy lore.

The platform delivers a privacy-preserving, cryptographically verifiable communication layer built on a federated relay network. The primary client is implemented in Python, optimized for TTY/SSH/tmux environments. The primary server stack is PHP, designed for clean module separation, horizontal scaling, and operational simplicity.

Key Architectural Properties

  • Terminal-first — keyboard-driven, minimal redraw, monochrome-capable
  • End-to-end encrypted — private messages use X3DH/PQXDH + Double Ratchet
  • Federated relays — minimized authority, no single point of failure
  • Cryptographic identity — no email required for account creation
  • Verifiable software — signed releases, Merkle integrity trees, atomic updates
  • Evidence-based trust — reputation system with Sybil resistance
  • Contribution-based economy — proof-of-service, not proof-of-work
  • Defense-in-depth — multiple security layers, honest about limitations
Design Principle

NYX never claims "100% secure," "unhackable," or "perfectly anonymous." The system uses technically precise language: tamper-evident, privacy-preserving, cryptographically verifiable, minimized-trust, and defense-in-depth.

Vision & Design Goals

Priority Order (When Requirements Conflict)

  1. Security — correctness of cryptographic boundaries
  2. Privacy — minimization of exposed metadata
  3. Correctness — protocol consistency, no silent data loss
  4. Reliability — graceful degradation under failure
  5. Decentralization — no single catastrophic trust point
  6. Performance — responsive under realistic constraints
  7. Developer Experience — clean APIs, good documentation
  8. Aesthetics — elegant terminal output, clean code

System Qualities

NYX should feel: dark, minimal, technical, mysterious, fast, privacy-oriented, developer-centric, distributed, modular, resilient, elegant, and hacker-inspired — without being childish or relying on fantasy aesthetics.

Section 04

Scope & Non-Goals

In Scope

  • Terminal-native messaging (DMs, groups, channels)
  • End-to-end encryption for private conversations
  • Federated relay network with trust/reputation
  • Cryptographic identity (no email required)
  • Signed software updates with integrity verification
  • Developer tools (Git integration, code snippets, AI assistant)
  • Plugin/extension system with sandboxing
  • Network token for anti-spam and service compensation
  • Distributed ledger for balances and transactions

Non-Goals

  • Replacing email or general-purpose social media
  • Perfect anonymity (metadata always partially observable)
  • Energy-intensive consensus (no PoW mining)
  • Storing ordinary chat on a blockchain
  • Server-side inspection of E2EE plaintext
  • Mobile-first GUI (terminal is primary)

§5 — User Model & Identity
Section 05

User Model & Identity

NYX identity is protocol-native and cryptographic. No email, phone number, or third-party OAuth is required for account creation. Email may optionally be linked later for account recovery.

┌──────────────────────────────────────────────────────────────┐ │ IDENTITY HIERARCHY │ ├──────────────────────────────────────────────────────────────┤ │ │ │ Account (nyx1...) │ │ ├── Identity Key Pair (Ed25519, long-term) │ │ │ ├── Device 1 ── Session Keys (X25519, rotating) │ │ │ ├── Device 2 ── Session Keys (X25519, rotating) │ │ │ └── Device N ── Session Keys (X25519, rotating) │ │ ├── Prekey Bundle (signed, for X3DH key agreement) │ │ ├── Optional: Recovery Key (encrypted, user-held) │ │ └── Optional: Email (recovery only, not identity) │ │ │ └──────────────────────────────────────────────────────────────┘

Key Types

Key TypeAlgorithmLifetimePurpose
Identity KeyEd25519Long-term (years)Sign identity operations
Device KeyEd25519Per-device, revocableDevice auth, message signing
Session KeyX25519Per-session, ratchetedE2EE key agreement
PrekeyX25519Until consumedAsync key establishment
Message KeyDerived (HKDF)Per-messageEncrypt messages (forward secrecy)
Recovery KeyX25519 + AES-256-GCMUser-managedEncrypted identity backup

Multi-Device & Recovery

  • Each device generates its own key pair, signed by the identity key
  • Sender encrypts separately for each active device key (fan-out)
  • Recovery: 24-word BIP39 mnemonic → derives recovery key
  • Lost device: Revoke via another device or recovery key
  • All devices lost: Recovery key required; without it, identity is unrecoverable
Privacy Note

An account with an attached email address is not anonymous. The email creates a linkable identity artifact. NYX clearly distinguishes between cryptographic pseudonymity and email-linked accounts.

Abstract Message Structure

// Abstract message envelope
  {
    "message_id":       "nyx_msg_01HQX...",      // UUIDv7 (time-sortable)
    "sender_id":        "nyx1qf3k...",            // Bech32 identity
    "device_id":        "dev_a7b2c...",           // Device fingerprint
    "conversation_id":  "conv_9x2m...",           // Conversation identifier
    "timestamp":        1703894400000,             // Unix ms (sender clock)
    "sequence":         42,                        // Per-conversation sequence
    "ciphertext":       "base64...",               // Encrypted payload (E2EE)
    "signature":        "base64...",               // Ed25519 sender signature
    "previous_hash":    "blake3_...",              // Hash chain (tamper evidence)
    "protocol_version": 3,                         // Protocol version
    "relay_metadata":   {                            // Optional relay-added fields
      "received_at": 1703894400123,
      "relay_id": "relay_x1...",
      "hop_count": 1
    }
  }
Encryption Boundary

For E2EE conversations, ciphertext contains the encrypted payload. The server stores only ciphertext. For public channels, the payload is plaintext protected by TLS in transit. signature covers all fields except relay_metadata.

Message Features

  • Replies: Threaded references via reply_to message ID
  • Mentions: @user and @channel with notification routing
  • Reactions: Emoji reactions stored as signed attestations
  • Editing: Signed edit records; original preserved in audit log
  • Deletion: Signed tombstone; content removed from client stores
  • Code snippets: Syntax-highlighted blocks with language tag
  • File sharing: Chunked, encrypted, resumable transfers

§11 — End-to-End Encryption
Section 11

End-to-End Encryption

Private DMs, private groups, and explicitly private channels use X3DH/PQXDH for initial key agreement and the Double Ratchet algorithm for ongoing message encryption. NYX does not invent new cryptography.

Session Establishment (X3DH)

ALICE (Sender) BOB (Recipient) │ │ │ 1. Fetch Bob's prekey bundle │ │ ─────────────────────────────────────────>│ (via relay) │ (IK_B, SPK_B, OPK_B[1..n]) │ │ │ │ 2. Generate ephemeral key EK_A │ │ 3. Compute DH values: │ │ DH1 = DH(IK_A, SPK_B) │ │ DH2 = DH(EK_A, IK_B) │ │ DH3 = DH(EK_A, SPK_B) │ │ DH4 = DH(EK_A, OPK_B[i]) │ │ 4. Derive SK = KDF(DH1‖DH2‖DH3‖DH4) │ │ │ │ 5. Send initial message + EK_A │ │ ─────────────────────────────────────────>│ │ 6. Bob computes same SK │ 7. Initialize ratchet chains │ │ │ ◄═══════ Double Ratchet active ═══════> │ │ (forward secrecy + post-compromise │ │ security via key ratcheting) │

Security Properties

PropertyMechanismGuarantee
Forward secrecyMessage key ratchetingCurrent key compromise ≠ past messages
Post-compromiseContinuous ratchetingRecovery after transient compromise
AuthenticationIdentity key signaturesVerifiably from claimed sender
Replay protectionSequence + timestampsDuplicate/old messages rejected
Out-of-orderMessage key indexingCorrect decrypt regardless of order
Device verificationSafety numbers / QRUsers verify shared keys

PQXDH (Post-Quantum Extension)

NYX recommends PQXDH which adds a post-quantum KEM (X-Wing / Kyber) to the X3DH key agreement. This provides hybrid classical + post-quantum security. Recommended

Section 13

Relay Server Architecture

Relay servers have minimized authority. A compromised relay cannot decrypt E2EE content or forge sender-authenticated messages. However, a malicious relay can still drop, delay, replay, or refuse traffic.

Relay Responsibilities

  • Accept authenticated messages from clients
  • Forward messages to recipient's relay (federation)
  • Store undelivered messages temporarily (offline queue)
  • Provide signed delivery receipts
  • Participate in health checks and reputation
  • Serve public channel content
  • Maintain user prekey bundles for X3DH

Relay Cannot Do

  • Decrypt private E2EE messages (no message keys)
  • Forge messages with valid sender signatures
  • Modify ciphertext without breaking AEAD
  • Silently drop messages without detectable failure

§14–15 — Multi-Relay Routing & Discovery
Section 14

Multi-Relay Routing

Clients maintain connections to multiple relays and select routes based on a composite scoring model, not just latency.

Server Selection Score

// Composite server selection score
  score = (
      w_latency    * normalize(latency_ms, 0, 2000) +
      w_packetloss * (1 - packet_loss_rate)        +
      w_uptime     * uptime_percentage               +
      w_reputation * reputation_score                +
      w_capacity   * available_capacity_ratio         +
      w_trust      * trust_level_normalized           +
      w_geo        * geographic_preference             +
      w_compat     * protocol_compatibility            -
      w_failures   * recent_failure_count              -
      w_abuse      * abuse_flag_score
  )

  // Weights (configurable, defaults):
  w_latency    = 0.20    w_reputation = 0.20
  w_packetloss = 0.10    w_capacity   = 0.10
  w_uptime     = 0.15    w_trust      = 0.15
  w_geo        = 0.03    w_compat     = 0.05
  w_failures   = 0.01    w_abuse      = 0.01
Anti-Manipulation

Reputation scores used in routing are not directly controllable by the server being scored. They are computed from independently verifiable evidence. A server cannot inflate its own reputation without detectable fraud.

§22–23 — Software Integrity & Merkle Tree
Section 22

Software Integrity

NYX uses a layered integrity mechanism that goes far beyond a simple folder hash.

LayerWhat It ProvesWhat It Cannot Prove
Source-tree integrityFiles match approved releaseThat this code is executing
Artifact integrityBuilt artifact matches sourceBuild environment was clean
Runtime integrityExecuting code matches disk filesOS/kernel not compromised
Environment integrityPHP version, extensions, configHardware untampered
Configuration integrityConfig not alteredSecrets not exfiltrated
Critical Distinction

A simple folder hash cannot prove what code is actually executing. An attacker with root access can modify the PHP runtime, inject opcache overrides, or use LD_PRELOAD — all without changing source files on disk.

Detection Capabilities

  • Modified files (hash mismatch against release manifest)
  • Missing files (expected file absent)
  • Unexpected files (unknown file in source tree)
  • Modified PHP code (per-file hash verification)
  • Downgraded versions (version constraint enforcement)
  • Unapproved plugins (plugin signature verification)

Explicit Limitations

Honest Disclosure

NYX cannot guarantee the following. These are fundamental limitations of the system design and the physical/digital world:

LimitationWhy
Perfect anonymityMetadata (timing, size, patterns) is always partially observable
Perfect availabilityNetwork partitions, DDoS, and infrastructure failures are inevitable
Absolute securityNew vulnerabilities discovered continuously; no system is invulnerable
Hidden metadata in all circumstancesNetwork observers can perform traffic analysis
Endpoint security on compromised devicesIf the user's device is compromised, all bets are off
Guaranteed delivery through malicious networkA coalition of relays can selectively drop messages
Perfect remote attestation on all platformsHardware attestation is platform-dependent
Perfect reputation integritySophisticated Sybil attacks may partially succeed
Zero risk in distributed consensusBFT has theoretical limits (⅓ malicious threshold)
