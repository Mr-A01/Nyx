§02 SYSTEM ARCHITECTURE

How it works

A layered architecture where each component has clear responsibilities, security boundaries, and failure modes.

network-visualizer.svg — Live Topology
Clients Relays Trust Ledger

→Message Flow

STEP 01
Key Agreement

Alice fetches Bob's prekey bundle via relay. X3DH/PQXDH computes shared secret.

STEP 02
Encrypt & Sign

Message encrypted with XChaCha20-Poly1305. Signed with Ed25519. Hash chain updated.

STEP 03
Relay Forward

Relay stores ciphertext only. Cannot decrypt. Forwards to recipient's relay.

STEP 04
Decrypt & Verify

Bob decrypts with ratcheted key. Verifies signature + hash chain.

x3dh-flow.txt — Session Establishment 
  ALICE (Sender)                                              BOB (Recipient)
      │                                                              │
      │  1. Fetch Bob's prekey bundle                               │
      │  ─────────────────────────────────────────────────────────>│
      │     (IK_B, SPK_B, OPK_B[1..n])                              │
      │  2. Generate ephemeral key EK_A                             │
      │  3. Compute DH values:                                      │
      │     DH1 = DH(IK_A, SPK_B)                                   │
      │     DH2 = DH(EK_A, IK_B)                                    │
      │     DH3 = DH(EK_A, SPK_B)                                   │
      │     DH4 = DH(EK_A, OPK_B[i])                                │
      │  4. Derive SK = KDF(DH1‖DH2‖DH3‖DH4)                       │
      │  5. Send initial message + EK_A ──────────────────────────> │
      │                                    6. Bob computes same SK  │
      │                                    7. Initialize ratchet    │
      │  ◄════ Double Ratchet active ════>                          │

What we solve

Communication is broken. Centralized platforms control your data, metadata exposes your patterns, and email gates your identity.

Built For

Honest Limitations

NYX never claims "100% secure" or "perfectly anonymous." We use technically precise language and are transparent about what we cannot guarantee:

•Perfect anonymity — metadata is always partially observable
•Perfect availability — network partitions are inevitable
•Absolute security — new vulnerabilities are discovered continuously
•Endpoint security on compromised devices

→ Optimization Techniques

asyncio

Non-blocking I/O for concurrent relay connections. No thread overhead.

MessagePack

Compact binary serialization. <200 bytes per message overhead.

Batching

Combine multiple ACKs into single round-trip. Reduce network overhead.

Incremental Sync

Delta-based with cursors. Only transfer what changed since last sync.

→ Anti-Sybil Mechanisms

MECHANISM

Identity Age

New accounts have limited trust. Cost to attacker: Time (weeks/months).

MECHANISM

Proof-of-Service

Reputation requires verifiable work. Cost to attacker: Resources.

MECHANISM

Resource Costs

Small token deposit for actions. Cost to attacker: Economic.

MECHANISM

Trust Endorsements

Existing users vouch for new. Cost to attacker: Social capital risk.

MECHANISM

Behavioral Analysis

Detect coordinated patterns. Cost to attacker: Operational complexity.

IMPORTANT

No PoW Mining

NYX does not require proof-of-work. Anti-Sybil costs are based on time, service, and economic deposits.

ABOUT THE STORY

The story behind NYX

Named after Nyx — the Greek personification of night. Darkness, silence, mystery, and the unknown as design philosophy.

Philosophy

NYX was born from a simple observation: the tools we use to communicate shape how we think about privacy, trust, and identity. Most messaging platforms treat these as afterthoughts — features to add later, if ever.

We started with a different premise. What if privacy wasn't a feature, but the foundation? What if the terminal — that most austere, most honest interface — was the primary way to communicate?

NYX is not a fantasy. It's not a game. It's a serious piece of infrastructure for people who take their digital lives seriously. Engineers, security researchers, infrastructure operators, and technical communities who need communication that works the way they work: quietly, efficiently, and without unnecessary noise.

Design Principles

Security First

Correctness of cryptographic boundaries above all else.

Privacy by Default

Minimization of exposed metadata, not an opt-in feature.

Honest Limitations

We never claim "100% secure" or "perfectly anonymous."

Developer-Centric

Clean APIs, good documentation, terminal-native experience.

Open & Verifiable

Open source, reproducible builds, signed releases.

Core Values

01

Transparency

Every cryptographic decision is documented. Every limitation is disclosed. No marketing promises — only technical reality.

02

Minimalism

Dark, quiet, focused. No unnecessary features. No bloat. Every component earns its place through utility.

03

Resilience

Federated, distributed, fault-tolerant. No single point of failure. No single point of trust.
